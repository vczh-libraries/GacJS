## Details

### Definition of Done

The task is complete when the TypeScript side can provide the existing
`rvmt::IViewModel` service to `RemotingTest_Core` with the same externally
visible behavior as `RemotingTest_RvmHost`:

- The implementation returns `Hello, <name>!` from `Translate`.
- It can run as an independently started Node.js process connected over the
  existing HTTP or MiniHTTP channel.
- It can run as a child started by `RemotingTest_Core /RVMT /Cli:<path>`; in
  this mode its RVM traffic uses redirected stdin/stdout while the separate
  GacJS renderer still uses Core's selected `/Http` or `/MiniHttp` server.
- The package produces a directly executable, platform-native Node launcher
  that Core can use as `<path>` and that accepts the exact appended `/Cli`.
- It can run inside the static browser bundle selected by `?rvmhost`.
- In browser mode the view-model host and renderer are two independent channel
  clients.
- Generated TypeScript bindings come from the x86 `RpcMetadata.txt` and
  `RpcMetadata.d.ts` inputs; contract IDs are not handwritten.
- The reusable RPC runtime implements the ownership, routing, initialization,
  and error behavior required by generated bindings.
- Existing renderer-only GacJS operation is unchanged.
- Codegen is deterministic and all package/unit/integration tests pass.

The first end-to-end contract is intentionally small:

- `rvmt::IViewModel` is an RPC constructor interface with type ID `0`.
- `rvmt::IViewModel.Translate` has method ID `1`.
- Its signature is `String -> String`.
- The deterministic service reference is
  `{clientId: <assigned host ID>, objectId: 0, typeId: 0}`.

This contract is the required implementation milestone for this task. The
general documents describe the complete reusable RPC surface, but that full
surface is not added to Definition of Done merely because it is documented.
The RVM milestone requires local constructor-service registration, string method
dispatch, login/declaration handling, incoming holds, exception responses, and
deterministic endpoint shutdown.

Use Workflow's larger metadata fixtures to test parsing, IR validation, naming,
and diagnostics. Proxy, inheritance, overload, property, event, collection,
by-value-slot, and finalizer support can land in the same change only when each
feature has its corresponding conformance tests. Otherwise generation must fail
with a source-located “unsupported” diagnostic as soon as such a construct is
reachable; it must never emit a partial binding or claim full-surface support.

### Scope and Non-Goals

In scope:

- A browser/Node-neutral Workflow RPC endpoint runtime.
- TypeScript generation for local service/object implementations required by
  the RVM contract, with runtime/IR boundaries that can add remote proxies and
  the remaining documented features without changing wire IDs.
- Refactoring the HTTP transport into a reusable channel client and a composed
  renderer adapter.
- A generated `rvm` binding package.
- A browser-safe host library plus a Node host with independently started
  network mode and Core-launched stdio `/Cli` mode.
- A Core-compatible, platform-native launcher for the Node `/Cli` mode.
- `?rvmhost` startup, failure propagation, tests, and documentation.

Explicit non-goals:

- A TypeScript broker, channel server, HTTP server, or replacement for
  `RemotingTest_Core`.
- Reimplementing the C++ RPC coordinator/requester or renderer handling owned by
  the core application.
- Adding RPC cancellation, deadlines, heartbeat messages, reconnect, or
  automatic retry of method calls.
- Changing Workflow's JSON schemas, IDs, or 64-bit numeric representation.
- Pretending that a remote TypeScript call is synchronous.
- Depending on garbage collection or process exit for correct remote cleanup.
- Hand-editing generated GacUI inputs.
- Combining the renderer and RVM logical channels into one transport client.
- Carrying renderer traffic over the RVM stdio connection.
- Treating `/Cli:<path>` as an arbitrary command line or changing the existing
  Core launch contract.

Both Node modes are client processes only; neither serves the static website or
listens on a port. In network mode the process is started independently and
connects to Core's HTTP/MiniHTTP channel endpoint. In exact `/Cli` mode Core
starts the process and owns its redirected stdin/stdout channel. The browser
mode runs completely in the static bundle that can be hosted by IIS or the
existing development static server.

Important conclusions from those sources:

- `RemotingTest_RvmHost` is an RPC endpoint/channel client, not a server.
- Core contains both a broker-side local client and a separate requester.
- A host is recognized only when it advertises exactly
  `ViewModelChannel` and `ViewModelReadyChannel`.
- Core accepts only one host and only during startup.
- Renderer clients are rejected until the requester's phase is `Running`.
- Host loss is deliberately fatal and replacement is not supported.
- `/Cli:<path>` is case-sensitive, valid only with explicit `/RVMT`, and does
  not choose the renderer transport. Core still requires `/Http`, `/MiniHttp`,
  or `/Pipe`, creates a renderer-only server, and creates a separate stdio-only
  RVM server.
- Core turns `/Cli:<path>` into `"<path>" /Cli`. The value is one executable
  path, not `node <script>` or another command plus arguments. On Windows it is
  passed directly to `CreateProcessW`, so a JavaScript file or npm `.cmd` shim
  is not a compatible target.
- Stdio carries the ordinary VlppOS channel strings as strict-UTF-8, canonical
  Base64, one message per ASCII line. Exact `!Exit` closes the connection;
  other `!`-prefixed lines are reserved and ignored.
- EOF handling is direction-asymmetric in the reference: the Core parent drops
  an unterminated partial line read from child stdout, while the `/Cli` child
  processes one nonempty final fragment from stdin before observing EOF.
- The positive ID in `<assignedClientId>;;` is the host's channel identity and
  initializes its local object references. It is distinct from the broker's
  later `serverClientId` in the RPC Login envelope.
- On shutdown the process-owning C++ server sends raw `!Exit`, closes child
  stdin, drains stdout, and waits without a timeout. The reference child exits
  immediately with status `1` on `!Exit`, EOF, or fatal I/O, while Core ignores
  that numeric status. Unexpected child/stdout loss before Core enters stopping
  produces exact `RemotingTest_RvmHost disconnected.`.
- The generated `RpcMetadata.d.ts` contains JSON value shapes only. Interface
  declarations and operation IDs come from `RpcMetadata.txt`. Generic envelopes
  and reserved negative IDs come from `Workflow/Release/Rpc.d.ts`.
- The owner records interested endpoint IDs in a set; it does not count wrapper
  instances.
- C++ calls are synchronously presented but remain reentrant by processing
  callbacks while waiting. TypeScript must preserve this through promises and
  concurrent dispatch.

### Phase 1: Refactor `remote-protocol-http`

The current module combines four concerns:

- Renderer-specific protocol imports and state handling.
- HTTP `Connect`/`Read`/`Write` requests.
- VlppOS channel-package framing.
- Send serialization, long-poll completion, and terminal failure handling.

Split it without changing renderer behavior.

#### Reusable HTTP channel client

Add a transport-facing API with:

- Configurable HTTP base URL/endpoint.
- One or more advertised channel names.
- Assigned local `clientId` after connection.
- Incoming packages carrying the server-supplied sender ID, channel name, and
  body.
- Direct send and broadcast send, with blocked receivers as an outgoing
  broadcast option.
- A distinguishable pre-assignment versus assigned connection state.
- A single terminal `completion` promise/result.
- Idempotent stop/close.

Keep the channel-client contract and the pure package parser/serializer
browser/Node-neutral and export them without renderer dependencies. The HTTP
implementation and the Node stdio implementation in `rvmhost` must satisfy the
same contract, including channel join, assigned-ID handling, send
serialization, completion, and stop. HTTP request URLs/long polling stay in
this package; stdio Base64 and process streams do not.

Support the direction-dependent framing syntax:

~~~text
receiverClientId;channelName;body                         // direct client to server
;channelName;body                                         // broadcast client to server
,blockedId[,blockedId...];channelName;body                 // excluding broadcast
senderClientId;channelName;body                           // server to client
~~~

The initial multi-channel join uses `!`:

~~~text
;;ViewModelChannel!ViewModelReadyChannel
~~~

The assignment response has the form:

~~~text
assignedClientId;;
~~~

Do not leave the renderer's current assumption of one numeric prefix inside the
generic parser. Validate every ID as a safe integer, preserve an empty channel
or body where the protocol permits it, and reject malformed separators rather
than accepting a partial parse.

Preserve these current transport properties:

- POST writes are chained so only one physical write is in flight.
- A write response can piggyback incoming packages and must be dispatched.
- The long-poll read loop and a write failure race to one terminal outcome.
- After a client ID has been assigned, a delivery/read/write failure is fatal.
- Stop and failure settle completion exactly once.
- Stop uses `AbortController` (or an equivalent injected fetch cancellation)
  so a pending connect/read cannot keep Node alive indefinitely.

Graceful session shutdown is ordered above the transport: stop new RPC work,
finalize the endpoint and await any required last writes while reads can still
dispatch, then abort the HTTP transport and await its completion. A transport
failure skips unreliable network cleanup but still finalizes local state.

Add tests for multi-channel negotiation, direct and broadcast frames, blocked
IDs, assignment, batched JSON bodies, piggyback responses, sequential sends,
terminal races, two concurrent independent connections, and prompt stop while
an idle long-poll fetch is outstanding.

#### Renderer adapter by composition

Keep the existing renderer-facing API where practical. Implement it as an
object that owns/uses the reusable HTTP channel client; do not subclass it.

The renderer adapter remains responsible for:

- `GacUIRemoteProtocol` channel selection.
- Renderer message serialization/binding.
- Core renderer target selection.
- Existing renderer state/completion behavior.

Generic HTTP code must not import generated renderer schemas or assume the core
renderer's client ID. Run all existing `HttpClientTest.ts` failure tests
unchanged or update them only for intentional public API changes.

### Phase 2: Add `gaclib/workflow-rpc`

Create a browser- and Node-neutral package containing reusable generic behavior
described in [`doc/rpc/Features.md`](doc/rpc/Features.md) and
[`doc/rpc/MemoryManagement.md`](doc/rpc/MemoryManagement.md).

#### Public runtime boundary

The RVM-required public boundary is:

- Generic direct/service envelope, object-reference, and exception types.
- Reserved generic operation IDs used by invocation, holds, and declarations.
- `RpcEndpoint` creation with an assigned client ID and abstract channel.
- Descriptor and codec registration.
- Local service registration before initialization.
- Initialization/login and cached declaration handling.
- Local object/reference conversion.
- Callee registration and deterministic lifecycle finalization.
- A local-object hold notification that settles only after an incoming
  `ObjectHold(true)` response has been written; include the reference and remote
  client so host composition can expose its `serviceHeld` near-barrier.
- Completion/fatal-error reporting.

When the matching full-surface features are implemented, extend that boundary
with by-value/event types, predefined collection/event IDs, remote service
discovery, typed outgoing invocation/proxies, event/suppression helpers, and
explicit proxy disposal. Do not publish no-op placeholders for deferred
features.

Keep internal request maps, lease maps, and local object maps private. Generated
descriptors should register behavior; they should not mutate those maps.

#### Dispatcher requirements

The RVM milestone must implement and test:

- Direct request/response validation, including source/target reversal.
- Broker `Login` handling.
- Pre-initialize outgoing service-declaration caching and incoming declaration
  caching/replay to waiters.
- Incoming `InvokeMethod` and `ObjectHold` operations, including the hold
  notification after its response write.
- `DeclareRemoteService` broadcast-and-drop with no response.
- User-thrown `RpcException` responses, separate from local protocol errors.
- Rejection of all pending calls/service waits on terminal failure.

The complete reusable surface additionally requires monotonic request IDs and a
pending-promise map, simultaneous/out-of-order outgoing calls, nested callbacks,
`EndInvokeMethod`, event broadcast/consolidation, and tagged remote-exception
decoding. Implement and test those together with generated proxy/event/by-value
support, or leave them behind an explicit unsupported-feature diagnostic for
this milestone.

Even in the RVM slice, the read loop must remain live while initialization or a
local implementation awaits. Do not serialize logical calls behind one
outstanding response. Serialize physical transport writes—HTTP POSTs for the
network client and stdout lines for the stdio client—while logical RPC calls
remain concurrent and responses may complete out of order.

#### Lifecycle requirements

The RVM milestone requires:

- A strong local-object table keyed by object ID.
- A `WeakMap` from local object to its stable active reference.
- A `Set<clientId>` of interests on each local object.
- The constructor-service owner hold.
- Listener/local-record cleanup and deterministic lifecycle finalization.

The complete proxy/object surface additionally requires:

- Remote typed-view interning by the full reference using `WeakRef`, with one
  shared hold lease per remote owner/object.
- A private proxy-to-reference `WeakMap`.
- Explicit awaited `dispose`/`release`.
- A generation-safe `FinalizationRegistry` fallback.
- Serialized hold reconciliation so a stale finalizer cannot unhold a
  replacement wrapper.
- Local/event/property cleanup and proxy invalidation on finalization.
- By-value return slots retained until `EndInvokeMethod`.

When that proxy surface is implemented, finalizer callbacks cannot await; they
may only enqueue cleanup and attach error handling. Tests must inject the cleanup
scheduler and deterministically reproduce the stale-finalizer and
in-flight-unhold races. Forced GC is supplemental only.

#### Serialization and numeric behavior

The RVM milestone needs strict string, object-reference, and exception schemas.
The complete surface adds generic known/unknown value helpers and predefined
collection behavior; generated codecs handle contract-specific types.

All 64-bit integer schemas currently map to JavaScript `number`. Reject values
outside the safe integer range instead of rounding. Do not substitute `bigint`
without a coordinated wire-schema change.

### Phase 3: Add `gaclib/codegen-workflow-rpc`

Follow the existing `codegen-remote-protocol` package pattern:

- The package compiles during `yarn run import`.
- It exports pure generator functions from its source entry.
- It has no `build` script.
- It has no package-local `codegen` script.
- Only `shared/codegen` invokes it during the repository codegen phase.

#### Inputs and parsing

The invocation receives explicit paths/contents for:

1. Normalized `RpcMetadata.txt`.
2. Generated `RpcMetadata.d.ts`.
3. A controlled output root.

Parse normalized Workflow syntax with a lexer/parser that keeps source
locations. Use the TypeScript compiler API for the `.d.ts` AST; do not use
regular expressions for TypeScript. Accept the current UTF-8 BOM and CRLF
inputs.

Build a validated IR containing:

- Enum/struct/value type structure.
- Interface IDs, constructor status, bases, and inheritance closure.
- Methods, parameter/result types, transfer modes, and overload identities.
- Events.
- Properties with getter/setter/event links and cache mode.
- Exact string and numeric IDs.
- Schema symbols and deterministic emitted TypeScript names.

Use metadata IDs verbatim. The Workflow compiler assigned numeric IDs from its
normalized global ID list; duplicating that algorithm would create a second
source of truth.

#### Validation and diagnostics

Fail before writing output for duplicate/missing IDs, reserved-ID collisions,
unresolved bases/types, unsupported normalized constructs, invalid property
links, schema disagreements, unsafe numeric IDs, ambiguous overload emission,
and flattened/sanitized TypeScript name collisions.

Diagnostics include input path, line, column, Workflow full name, and the
relevant ID. Never recover with `any` or a guessed ID.

#### Generated source

For the RVM milestone generate:

- Contract value/application types.
- Exact ID constants and descriptor maps.
- Strict codecs for all reachable RVM value shapes.
- Callee dispatch tables.
- Constructor-service registration helpers.
- Endpoint setup for all descriptors/codecs.

The complete generator target additionally emits asynchronous proxy interfaces
and callers, type/inheritance recognition, generic known/unknown codecs, proxy
factories, property cache/dynamic getter glue, and event attach/detach,
invocation, and suppression glue. Enable each output family only with its
matching runtime implementation and conformance tests.

Local implementation methods may return `T | Promise<T>`. When proxy support is
implemented, proxy methods return `Promise<T>`. Because TypeScript is
structurally typed, registration must use a generated descriptor/token;
matching method names alone do not establish an RPC type ID.

The supplied `.d.ts` may be ambient and `tsc` does not necessarily copy source
declarations to build output. Emit an owned `.ts` type module from the validated
schema, or add an explicit deterministic copy step, so the generated package is
self-contained after build.

Emit only into a manifest-owned generated subtree. Use stable ordering, no
timestamp/absolute path, fixed encoding/newlines, write-if-changed, and safe
removal of obsolete generated files. Two identical runs must be byte-identical.

#### Generator tests

Copy representative fixtures into the generator test package rather than
reading unbuilt sibling repositories at test time. Include Workflow-generated
cases to prove parsing/IR/diagnostics for:

- Primitives and numeric boundaries.
- Enums/flags and structs.
- Nullable and nested list/map/observable-list types.
- By-value and by-reference transfers.
- Interface references and callbacks.
- Inheritance and multiple inheritance.
- Overloads.
- Events.
- Cached and dynamic properties.
- Invalid/collision diagnostics.

For every feature not emitted in the RVM milestone, assert the precise
source-located unsupported diagnostic. Replace that negative fixture with
generated/typecheck/runtime goldens when the feature is implemented.

Add a golden for the real `rvmt::IViewModel` contract that asserts IDs `0` and
`1` and the complete generated file set.

### Phase 5: Add `website/rvmhost`

Create a transport-neutral host session and two entry surfaces.

The common session accepts an already connected channel client that advertises
exactly `ViewModelChannel` and `ViewModelReadyChannel`. It owns the generated
endpoint, `IViewModel` implementation, Ready/Initialize sequence,
`serviceHeld`, completion, and idempotent stop. It must not use `fetch`, the DOM,
or Node process streams. This prevents the HTTP and stdio modes from acquiring
different RPC lifecycle behavior.

#### Browser-safe library

`src/index.ts` must be safe to bundle for a browser:

- No import of `process`, `child_process`, filesystem, or other Node-only APIs.
- Accept origin/base-path configuration.
- Create a dedicated HTTP connection advertising exactly
  `ViewModelChannel` and `ViewModelReadyChannel`.
- Create and configure a Workflow RPC endpoint with the assigned client ID.
- Register the generated `IViewModel` service before dispatcher initialization.
- Implement `Translate(name)` as `Hello, <name>!`.
- Send the control Ready payload as the JSON-channel batch `["Ready"]`.
  Its client-to-server network package is the broadcast
  `;ViewModelReadyChannel;["Ready"]`.
- Call endpoint initialization immediately after sending Ready. Initialization
  must keep reading while it waits for broker Login, then flush the cached
  service declaration.
- Expose a `serviceHeld` near-barrier that resolves after the first external
  service hold response write, plus terminal completion and idempotent stop.
  `serviceHeld` deliberately does not claim that Core is already `Running`.

Do not call this component an RPC server in its API or docs. It is a local
service owner connected as a channel client.

#### Node CLI

Put Node-only code in the separately exported `src/cli.ts`. Select exactly one
of these modes:

- Exact single argument `/Cli`: Core-launched stdio mode. The spelling and case
  match `RemotingTest_RvmHost` and Core's appended argument.
- Any documented network options, with no `/Cli`: independently started
  HTTP/MiniHTTP mode.

Reject mixed modes and unknown arguments before opening a channel. Keep all
Node-only imports outside the browser entry graph.

Use this exact network-mode grammar; each value option appears at most once and
options may be reordered:

~~~text
gacjs-rvmhost [--origin <http-or-https-origin>]
                [--base-path </absolute-endpoint-path>]
                [--service-only]
~~~

Zero arguments selects network mode with the defaults below and enables the
renderer readiness probe. `/Http` and `/MiniHttp` are Core-side server
selectors, not TypeScript CLI flags: both expose the same fetch endpoint, so
reject those aliases rather than pretending that the child selects Core's
transport. Require a value after `--origin`/`--base-path`, validate it, and
reject duplicates, unknown options, positional arguments, or any network flag
combined with exact `/Cli` before performing I/O.

##### Independently started network mode

This mode should:

- Parse origin/base-path options with `http://localhost:8888` and
  `/GacUIRemoteProtocolHttp` as documented defaults.
- Start the same browser-neutral host library.
- Print `GACJS_RVMHOST_SERVICE_HELD` when `serviceHeld` resolves. This line is a
  service-availability near-barrier, not renderer readiness.
- In the default Core mode, then open a temporary raw `GacUIRemoteProtocol`
  channel as a readiness probe. Retry only untyped pre-assignment closes with
  fresh transports. Once the probe receives an assigned ID, stop it and await
  its cleanup; that assignment proves Core reached `Running` and renderer
  replacement is allowed.
- Print the exact machine-readable line `GACJS_RVMHOST_READY` only after the
  probe succeeds, and never print it on partial setup.
- Provide an explicit `--service-only` mode that skips the renderer probe and
  never prints `GACJS_RVMHOST_READY`. This mode exists for service-only
  coordinators such as `CppTest_Rvm`, which reject every renderer channel.
- Remain alive until completion or a termination signal.
- Set a nonzero exit code and write a useful diagnostic on terminal failure.
- Finalize/stop idempotently on process termination.

It must not start a static-file or HTTP server. Tests spawn the built CLI as the
manually started network-protocol equivalent of `RemotingTest_RvmHost`.

##### Core-launched stdio `/Cli` mode

Implement a Node-only stdio string transport under `rvmhost`; do not put Node
streams in `workflow-rpc`, generated `rvm`, or `remote-protocol-http`:

- Wrap every outgoing VlppOS channel string as strict UTF-8, standard canonical
  Base64, followed by one `\n`.
- Accumulate arbitrary stdin chunks, accept both LF and CRLF, and process every
  complete ASCII line in order. Strip at most one trailing CR. At stdin EOF,
  process one nonempty unterminated final fragment before reporting the
  disconnect; an empty EOF contributes no line. This matches the child-side
  `Console::TryRead` path and deliberately differs from the process-owning
  server's pipe reader, which discards a partial child-output line. Reject lone
  UTF-16 surrogates before outbound UTF-8 encoding and use fatal UTF-8 decoding
  inbound.
- Treat exact `!Exit` as Core-requested shutdown. Ignore other
  `!`-prefixed control lines, matching the C++ transport. Invalid/noncanonical
  Base64, non-ASCII lines, and invalid UTF-8 are ignored for compatibility and
  must not reach the channel parser.
- Once a canonical frame decodes, malformed `NetworkPackage`/JSON and the
  channel-layer `!Error` package are fatal. Do not confuse that encoded
  `!Error` channel with the raw stdio `!Exit` control line.
- Run the normal channel join and assignment inside the encoded lines. The
  first outbound payload is the same
  `;;ViewModelChannel!ViewModelReadyChannel` join used in network mode; after
  assignment, reuse the common host session and identical Ready/Initialize
  order. Use the C++-compatible Base64 golden
  `OztWaWV3TW9kZWxDaGFubmVsIVZpZXdNb2RlbFJlYWR5Q2hhbm5lbA==` for that join.
  Parse `<assignedClientId>;;` from Core and never assume the commonly observed
  ID `3`. The Ready broadcast above must encode as the second C++ golden line
  `O1ZpZXdNb2RlbFJlYWR5Q2hhbm5lbDtbIlJlYWR5Il0=`.
- Serialize stdout writes and honor stream backpressure. Stdout is exclusively
  protocol traffic: never print banners, readiness markers, diagnostics, test
  output, or `console.log` there. Send diagnostics to stderr.
- For black-box process-tree tests only, honor
  `GACJS_RVMHOST_PID_FILE=<absolute-temp-file>` by writing the child's decimal
  PID to that file without touching stdout. The harness owns the unique file;
  normal launches do not set this variable, and runtime correctness must not
  depend on it.
- Do not open an HTTP RVM connection, renderer readiness probe, or retry loop.
  Core owns the stdio RVM server and does not admit its separate renderer until
  the requester has acquired the declared service. The browser harness waits
  for Core's automation window before connecting its normal renderer.
- On `!Exit`, stop all protocol work and terminate promptly without echoing
  `!Exit` or attempting unavailable wire cleanup. First perform deterministic
  local-only finalization: abort local work, reject pending operations, detach
  stream/channel listeners, and clear endpoint maps; then explicitly exit.
  This local cleanup must not wait on Core or rely on the process exit itself.
  The reference child exits with code `1` for this and every other
  disconnection, and Core deliberately ignores the child's numeric status;
  match that observable process behavior. Unexpected EOF, broken stdout,
  invalid channel framing, or host failure follows the same local-finalization
  path, settles completion once, reports on stderr when possible, and exits
  with code `1`.
- Do not depend on the numeric child exit code being observed by Core. Core
  detects loss through stdout EOF, and a child that does not exit after
  `!Exit` can block Core shutdown indefinitely.

The HTTP renderer remains a different client on Core's renderer-only server.
No renderer bytes or renderer client ID pass through the child's stdio stream.

##### Core-compatible launcher

`/Cli:<path>` accepts one directly executable path. Core constructs
`"<path>" /Cli`; it cannot express `node lib/src/cli.js`, and Windows
`CreateProcessW` cannot use the npm `.cmd` shim as that executable. Therefore
the package build must also produce a platform-native Node single-executable
application (SEA):

- Bundle the Node CLI and all runtime dependencies into one CommonJS `.cjs`
  file with a directly declared `esbuild` dependency. Only Node built-ins may
  remain external; do not point SEA preparation at the normal ESM build tree.
- Using the same supported Node executable for blob generation and injection,
  generate a SEA blob with
  `useSnapshot: false`, `useCodeCache: false`,
  `disableExperimentalSEAWarning: true`, and `execArgvExtension: "none"`; copy
  `process.execPath`, then inject the blob using a directly declared,
  lockfile-pinned `postject` build dependency. Disabling exec-argument extension
  prevents inherited `NODE_OPTIONS` from changing a Core-owned protocol child.
- Emit the stable `lib/bin/gacjs-rvmhost(.exe)` path named above. Build it
  natively on Windows, Linux, and macOS; perform the required Mach-O signature
  removal and ad-hoc re-signing on macOS.
- Pass a resolved absolute launcher path. Core's existing quoting supports
  ordinary spaces, which must be tested, but its POSIX `/bin/sh -c` path does
  not robustly escape every possible shell-special filename; document that
  inherited limitation instead of broadening `/Cli:<path>` into a command line.
- Enforce the manifest/runtime range and fail with an actionable diagnostic on
  an unsupported or incapable toolchain. SEA is still an active-development
  Node feature, so producing and executing the artifact is a release gate, not
  an assumed side effect of TypeScript compilation.
- Do not commit copied Node executables or transient SEA blobs. The package
  build owns and cleans its launcher outputs just like other `lib` artifacts.

The ordinary `lib/src/cli.js`/npm bin remains useful for manually started
network mode. Documentation and tests must never pass it, a `.js` file, a
shebang script on Windows, a package-manager `.cmd`, or a string containing
`node <script>` as Core's `/Cli:<path>`.

### Phase 6: Implement `?rvmhost` in `website/entry`

Add `rvmhost` as an entry-package dependency. Detect the option with:

~~~ts
new URLSearchParams(location.search).has("rvmhost")
~~~

The existing static server resolves `URL.pathname`, so
`/index.html?rvmhost` continues to serve the same static file. The current
esbuild entry creates one browser IIFE; keeping the imported host entry
browser-safe lets it be included in that bundle without a web application
server.

The current lifecycle is split between
`Gaclib/website/entry/src/index.ts`, whose `runGacUI` returns
`[renderer, client]`, and `assets/index.html`, which starts the client and owns
mask/error cleanup. Add a composite session/start API with `startup`,
`completion`, and `stop` for query mode, export it from `src/index.ts`, and
update `assets/index.html` to select it from the query string. Preserve the
existing `runGacUI` signature and no-query behavior for current callers. The
HTML must not reach into private RVM-host or transport state.

#### Two-client requirement

In query mode create two completely independent HTTP client instances:

~~~text
RemotingTest_Core
  ├─ client A: ViewModelChannel + ViewModelReadyChannel
  │              TypeScript IViewModel service owner
  └─ client B: GacUIRemoteProtocol
                 renderer
~~~

They must receive distinct client IDs, run distinct long-poll loops, own
distinct completion state, and be stopped separately. Never advertise all three
channels on one connection; Core uses the exact channel set to classify clients.

#### Startup barrier

The C++ order to preserve is:

~~~text
connect host channels and obtain client ID
  -> configure generated endpoint
  -> register IViewModel (declaration cached)
  -> send ["Ready"] on ViewModelReadyChannel
  -> call endpoint Initialize immediately
  -> Core processes Ready, registers the accepted host with the broker,
     and the broker sends Login
  -> Initialize observes Login and flushes the cached declaration
  -> Core requester acquires service and enters Running
  -> connect renderer client
~~~

Renderer admission before `Running` is rejected, so “start both promises” is
incorrect. Flushing the service declaration alone does not prove that the Core
requester has finished acquiring it.

There is no definitive post-`Running` notification visible to the host. Use the
strongest existing near-barrier: wait until the Core requester sends
`ObjectHold(true)` for the service and the host has completed the corresponding
response write. Core calls `BeginRunning()` immediately after that request
returns, but a small admission race remains. Therefore `?rvmhost` must create a
fresh renderer transport and retry only its initial channel assignment when the
attempt closes before receiving an assigned client ID.

VlppOS sends neither an assignment nor a typed error when Core rejects a pending
client; it simply closes that connection. Consequently query mode cannot prove
that a pre-assignment EOF/non-200 means “pre-running rejection.” While the
accepted host remains healthy and query-mode startup is pending, treat any such
pre-assignment termination as retryable, record it for diagnostics, discard the
entire transport, and create a new one. Stop on successful assignment, host
failure, or page abort. After assignment, every failure is terminal.

This is transport bootstrap retry only. Do not retry RPC invocations and do not
change the normal renderer client's terminal/no-reconnect contract. Test the
rejection race deterministically with a fake channel server that delays its
Running-equivalent state past the first renderer attempt; the normal JavaScript
harness cannot inject a `BeginRunning()` delay into the real Core. Also run a
repeated real-Core startup stress test to cover the production scheduling path.

Review the bootstrap against the existing TaskQueue warning in
`GacUI/ToDo/1.4.2.0.md`. Waiting for a signal must not stop the host read loop:
login, service requests, holds, or callbacks can be required to make Core reach
`Running`.

#### Session completion and replacement

Across startup and the active session, monitor both completion promises:

- A host failure during startup cancels renderer bootstrap and fails startup.
- After the renderer is running, host failure records a terminal host outcome
  but does not eagerly stop the renderer or replace the page with the host
  transport error. Core only injects `RemotingTest_RvmHost disconnected.` into
  its requester; retain the renderer so the next UI-triggered `Translate` can
  observe that injected exception and receive Core's exact ErrorChannel text.
  Do not add an automatic RPC solely to force this observation. Record the host
  outcome separately; post-startup host failure alone must not settle the
  composite page completion or display a competing generic mask.
- Renderer failure or replacement does not stop/finalize the host; Core supports
  replacing renderer clients while the accepted RVM host remains connected.
- Normal page teardown stops both idempotently.
- Track host and renderer outcomes separately, and do not let cleanup errors mask
  the failure being reported.

Host disconnect remains fatal to Core with the existing
`RemotingTest_RvmHost disconnected.` behavior once an RPC observes the injected
exception. Do not add host replacement or automatic reconnect. A page that
deliberately owns both clients still stops both when it unloads; retaining the
renderer to receive Core's post-host-loss fatal error and renderer replacement
while the page remains alive are the exceptions to symmetric ownership.

Without `?rvmhost`, call the existing renderer startup directly and preserve
current behavior and bundle output.

### Implementation Order and Review Gates

Use these gates so an end-to-end demo cannot hide missing fundamentals:

1. **Transport gate:** reusable HTTP channel tests pass; renderer regression is
   unchanged.
2. **Runtime gate:** the RVM-required in-memory dispatcher/lifecycle tests pass,
   including initialization, invocation, holds, exceptions, and finalization.
3. **Generator gate:** representative Workflow fixtures parse or produce the
   expected unsupported diagnostics, and the RVM golden is deterministic.
4. **Binding gate:** generated `rvm` binding dispatches `Translate` through the
   in-memory runtime with IDs `0`/`1`.
5. **Stdio/launcher gate:** the strict stdio codec passes fake-parent tests, the
   native SEA is built and smoke-tested on the current platform, and no
   Node-only import enters the browser graph.
6. **Network Node gate:** the independently started CLI passes `CppTest_Rvm`
   network mode and replaces `RemotingTest_RvmHost` against the C++ core.
7. **Core-launch gate:** `CppTest_Rvm /Cli:<SEA>` and
   `RemotingTest_Core /RVMT <renderer-transport> /Cli:<SEA>` auto-launch the
   child, acquire the service, and stop/reap it without a hang.
8. **Browser gate:** `?rvmhost` uses two clients and reaches the UI without an
   unrecovered admission race; renderer replacement preserves the host.
9. **Regression gate:** renderer-only behavior and the complete platform matrix
   pass; a second codegen run is clean.

Add a separate full-surface conformance gate when proxy, inheritance, property,
event, collection, by-value-slot, or finalizer features are implemented. The RVM
gate neither requires nor certifies those optional features.

At each gate, review the generated/runtime boundary: contract-specific IDs or
codecs belong in generated `rvm` sources; generic routing and ownership belong
in `workflow-rpc`; the pure VlppOS package codec and HTTP request loop belong in
`remote-protocol-http`; Node Base64-line framing, application behavior, and
process/browser composition belong in `rvmhost`.

### High-Risk Review Checklist

- `RpcMetadata.txt` and `RpcMetadata.d.ts` are not used interchangeably.
- Generic envelopes/predefined negative IDs are supplied by `workflow-rpc`.
- No generated ID is recomputed.
- The HTTP parser supports complete multi-client/channel framing.
- In `?rvmhost` and independently started network-host modes, renderer and RVM
  use distinct HTTP sessions/client IDs; in `/Cli` mode RVM uses stdio instead.
- Exact `/Cli` is the sole argument in stdio mode; it is never combined with
  origin, base-path, readiness-probe, or `--service-only` options.
- Core `/Cli:<path>` receives the platform-native SEA, never a `.js`, npm
  `.cmd`, shebang placeholder on Windows, or `node <script>` command string.
- Stdio frames are strict UTF-8 in canonical Base64 with LF/CRLF streaming,
  partial-line, backpressure, and invalid-input behavior matching C++.
- Stdio stdout contains protocol lines only; banners, readiness markers, and
  diagnostics are forbidden, and `/Cli` opens no HTTP RVM client or renderer
  readiness probe.
- Raw `!Exit`, unexpected EOF, and broken-pipe behavior terminate promptly and
  cannot leave Core blocked while reaping its child.
- `/Cli` performs deterministic local endpoint/map/listener cleanup before its
  explicit status-`1` exit and does not attempt unavailable wire cleanup.
- Core-launch shutdown verification uses automation `!Exit` plus the child PID,
  not the harness's process-tree force-kill; host-loss verification retains an
  active renderer before killing that exact child.
- Every host-loss assertion triggers a subsequent/in-flight `Translate` to
  expose Core's injected exception; query-mode cleanup does not preemptively
  stop the renderer or mask Core's exact fatal text.
- The SEA is bundled completely, built/tested natively on each supported
  platform, and its active-development Node engines range, CI matrix,
  capability check, and `postject` lock are explicit.
- Local service registration precedes endpoint initialization.
- Ready is the JSON batch `["Ready"]` on the separate ready channel.
- Initialize is called immediately after Ready and itself waits for Login.
- The host read loop remains active during bootstrap.
- An untyped pre-assignment renderer close is retried with a fresh transport
  only during query-mode bootstrap or the default independently started
  network-CLI readiness probe.
- Renderer replacement does not stop the accepted host.
- Transport stop aborts an outstanding long poll.
- Logical RPC requests can interleave and reenter.
- Every accepted direct request receives a response.
- Object interest is per client, not per proxy instance.
- Endpoint finalization is deterministic.
- When proxy support is enabled, tagged `RpcException` is detected before result
  deserialization, explicit disposal is deterministic, and generation-safe
  interning prevents stale unholds.
- When by-value returns are enabled, storage is released with
  `EndInvokeMethod` in `finally`.
- 64-bit unsafe integers are rejected, not rounded.
- Node-only stdio, SEA, filesystem, and process imports cannot enter the
  browser-safe module graph.
- Terminal errors settle once and cleanup cannot hide the original failure.
- There is no invented method retry, heartbeat, timeout, or host replacement.
- Generated `rvm` binding output is self-contained, manifest-owned, and
  byte-deterministic; the separately built SEA is functionally gated instead.
